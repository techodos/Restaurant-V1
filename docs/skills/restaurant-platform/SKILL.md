## 1. Overview

Multi-tenant restaurant storefront: menu, cart, guest/customer checkout, table reservations, reviews, order tracking, email and push notifications. Routes live under `/r/[restaurantSlug]/...`; `/` redirects to the default restaurant. Only the customer storefront exists; staff/admin UI is not built (auth service and permissions are ready for it). Stack: Next.js 15 (App Router, server actions), React 19, Tailwind 4, `pg` (no ORM), zod, jose, decimal.js, vitest, Playwright. Demo tenants: Bella Napoli `bella-napoli` (main seed), Sakura (isolation fixture), Zaytoun `zaytoun` and the cafe Blue Hour Coffee `blue-hour` and the buffet Villa The Grand Buffet `villa-grand-buffet` and the burger brand Bun Intended `bun-intended` (own seeds, section 18); test fixtures are in `tests/helpers/db.ts`.

## 2. Architecture

One Next.js app today, laid out so the backend can be lifted out and so a restaurant can later get its own database without touching business logic.

```
src/app, src/components      UI. Pages/layouts/server actions (thin)/React components
        ↓
src/web                      Next.js glue: cookies, session, request cache, notFound(), theme CSS, seo, media
        ↓
src/server/services          Use cases (business rules). Framework-free
   ├ src/server/validation   zod input schemas        ├ src/server/domain  pricing engine (pure)
        ↓
src/server/repositories      SQL, one file per aggregate; rows → domain models (db/mappers.ts)
        ↓
src/server/db                getDb(scope) → registry → DatabaseManager → Database (pg pools + RLS context)
        ↓
PostgreSQL / Supabase        db/migrations/*.sql is the schema (RLS, triggers, roles)

src/shared                   Isomorphic: models, enums, settings schemas, money, hours, ordering, order-timeline,
                             order-live, notification-channels, utils
src/server/config            The ONLY reader of process.env
```

Aliases: `@/*` → `src/*`. Boundaries are enforced by `tests/architecture.test.ts` (run it after structural changes):
- `server/` and `shared/` import no `next`, `react`, `@/web`, `@/components`, `@/app`; `shared/` imports no `@/server`.
- `app/` and `components/` never import `@/server/repositories`, `@/server/db`, `@/server/context`, `auth-service`, `tokens`.
- `server/services` and `server/domain` never import `@/server/db` or `pg`.
- `new Pool(` only in `server/db/database.ts`; `process.env` only in `server/config/`.
- Order code never imports Resend/FCM; live-order code imports none of the notification code (`tests/order-events.test.ts`).

Types: DB rows (`Row`, snake_case) exist only inside repositories and `db/mappers.ts`; domain models are `shared/contract/models`; API envelopes are `ApiResult`/`ApiError`; UI props are declared by the component.

### Request context and multi-tenancy

- `RequestContext` (`server/context.ts`) = `{userId, restaurantId, customerId, cartToken, actor}`. `web/session.ts#getVisitorContext` derives it from cookies; services pin the tenant with `forRestaurant(id, ctx)`. `restaurantId` is both the RLS pin and the DB routing key.
- Repositories obtain a database only via `getDb({ restaurantId })` or `getDb(ctx)`; platform lookups (slug resolution, public restaurant list) use `getDb()`. Then `db.read(ctx, tx => …)` (runtime role, RLS enforced) or `db.write(ctx, tx => …)` (service role, for authorised writes). Each call is one transaction that sets `app.*` settings with `set_config(..., true)` so RLS policies see it and nothing leaks between pooled connections; do not nest transactions.
- Isolation is enforced by RLS (unprivileged `app_runtime` role) and re-checked in services (`resolveCustomer` rejects a session issued for another restaurant; `requireLine` rejects foreign cart items).
- Today one database serves everyone (`SingleDatabaseDirectory` in `server/db/registry.ts`); see section 13 for per-restaurant databases. Do not implement it unless asked.

### Error handling

`AppError` (`errors.notFound|unauthorized|forbidden|validation|conflict|rateLimited|internal|custom(code,msg)`) and `PricingError extends AppError` are the only errors shown to users. `toApiError` maps zod, Postgres and unknown errors to a safe `ApiError`; `action(fn)` (server actions) and `jsonError(e)` (route handlers) are the two edges that convert and log through `server/logger.ts` (never `console.*`). Database messages and stack traces never reach the client.

### Configuration

`config.app | database | storefrontCache | auth | storage | payments | email | push | notifications | orderEvents`. Each section parses only its own variables the first time it is used, so importing config has no side effects and a missing variable fails with its **name** (never its value). `.env.example` lists every variable.

## 5. Rules easy to break

1. Money is `string` (2 dp) everywhere; compute with `shared/money` / `server/domain/pricing`. Never `number`. Prices are recomputed server-side from the DB; the browser sends ids, quantities and notes only.
2. Guest access is proven with the cart token (httpOnly cookie `rp_cart`). Anything that reads an order or cart as a guest must pass `cartToken` in the context (`getVisitorContext` does).
3. Website `theme`, `settings`, `features`, `sections` are untrusted JSONB: parse with the zod schemas in `shared/contract/settings|sections`, never read raw.
4. Order status is a DB-enforced state machine with `order_status_history`; UI must not decide transitions.
5. Permissions exist in SQL (`app.role_permissions()`) and TS (`server/auth/permissions.ts`); change both plus a migration; `tests/rbac.test.ts` checks parity.
6. Do not expose DB/system messages to clients: throw `errors.*`/`AppError`; unknown errors become a generic INTERNAL_ERROR.
7. Never call a repository from a page, component or action; add or extend a service.
8. `revalidatePath` and `notFound()` belong to `app/`/`web/`, not services.
9. Never send email/push from order or admin code; only commit the change and (after the response) call `dispatchDueNotifications`.
10. There is no database cart (section 20). The tray is a browser cookie (`rp_tray_<slug>`) written by `useLocalCart()` only — adding/changing/removing lines makes no request. Any new UI that changes tray contents goes through `useLocalCart()`; anything that reads it server-side goes through `web/storefront.ts#readTray`/`readTrayView` (priced from the snapshot, never the DB). The only database work in ordering is `createOrder`, one transaction; do not add reads before it (restaurant/customer/menu/zones/coupon are all read inside it). Never identify the signed-in customer from the database on a page view: `getStorefrontCustomer` reads the signed JWT (section 16).
11. A payment method must be valid for the order type (`PAYMENT_METHOD_ORDER_TYPES`, `shared/contract/enums.ts` — e.g. `cash_on_delivery` is delivery-only, `cash`/`card_terminal` are pickup/dine-in-only). Checked in three places: `getCheckoutOptions` (server-rendered initial list), `checkout-form.tsx`'s `availablePaymentMethods` (re-filters client-side when the customer switches order type on the checkout page itself, since that doesn't re-render from the server), and `createOrder` (the real, unbypassable boundary). Add a payment method to `ONLINE_PAYMENT_METHODS`/`PAYMENT_METHODS` and you must also add it to `PAYMENT_METHOD_ORDER_TYPES` or it defaults to unavailable everywhere.
12. A menu item flagged `isBuffetPackage` (priced per head, e.g. Villa The Grand Buffet's "The Grand Dinner") can only be ordered as `dine_in`. The tray is a browser cookie (section 20), so nothing is refused at "add": `services/cart.ts#viewTray` flags a buffet line as unorderable (`problem`) whenever the tray's order type is not dine-in — the cart shows it, the checkout page lists it as a blocker — and `createOrder` refuses it (`BUFFET_REQUIRES_DINE_IN`) as the final check (`orderableItemsSql` selects `is_buffet_package` for that). (Master's DB-cart version checked it in `addToCart`/`changeOrderType`; ported 2026-09-29.) `restaurants.features.alaCarteEnabled` (default true) hides every non-buffet category/item from the storefront menu when off (`services/catalog.ts`) — snapshot-only; the rare `STOREFRONT_CACHE_ENABLED=false` debug path is intentionally left unfiltered rather than adding a surprise DB call there (see `tests/storefront-services.test.ts`, which pins that path's repository call graph).
13. `settings.serviceFee` is one independent `{enabled, rate}` pair per order type (`delivery`/`pickup`/`dine_in`), not one shared rate across whichever types were checked — `pricing.ts` reads `settings.serviceFee[orderType]`. Old-shape stored JSONB (`{enabled, rate, orderTypes: OrderType[]}`) is upgraded on read by `migrateServiceFeeShape` (`shared/contract/settings.ts`), called once at the DB-row boundary (`db/mappers.ts#mapRestaurant`) — not a schema-level `z.preprocess`, because `server/validation/settings.ts` needs `restaurantSettingsSchema.shape.serviceFee` to stay a plain `z.object(...).default(...)` for `.removeDefault().partial()` to work.
14. **Customer self-cancellation (added 2026-09-27)** is admin-configurable, separate from staff cancellation (`/admin`, always allowed regardless of this rule): `settings.ordering.customerCancellation` = `{enabled, allowedPaymentMethods, cutoffStatus}`. `shared/order-cancellation.ts#canCustomerCancelOrder(order, settings)` is the one place this is interpreted (pure, no I/O) — it returns false once the feature is off, the order's `paymentMethod` isn't in `allowedPaymentMethods` (default excludes the online methods, `card_online`/`wallet`/`bank_transfer` — cancelling an online-paid order does not refund it, so it is opt-in, not default-on), the order is already terminal, or `ORDER_STATUS_RANK[order.status] > ORDER_STATUS_RANK[cutoffStatus]` (default cutoff `pending`, i.e. "only while not yet confirmed"; admin picks from `CANCELLABLE_ORDER_STATUSES`, the non-terminal statuses). Wired at `/r/<slug>/order/<number>` (`canCancel` computed server-side in `page.tsx`, gates whether `<CancelOrderButton>` even renders) and enforced for real by `services/orders.ts#cancelOrderByCustomer` (called from `order/actions.ts#cancelOrderAction`, which re-fetches the order via `findVisitorOrder` first — ownership proof, never trusted from the click — so a status change that happened moments ago is caught, not a stale render). The DB transition trigger (section 6) is a second backstop: it refuses `cancelled` from `completed`/`cancelled` regardless of this app-level check. Cancelling queues the same `cancelled` notification event as a staff cancellation (push only, no email — section 7's matrix), so `cancelOrderAction` calls `dispatchDueNotifications` in `after()` like every other status-changing action. Admin controls live in the existing **Ordering** settings card (`settings-sections.tsx#OrderingSection`), not a new section. No automatic refund is issued for any cancellation (customer- or staff-initiated) whatever the payment method — staff must refund manually via the payment provider if one was ever enabled for online-paid orders. **Bug, same day:** the first version passed the signed-in visitor's `userId` straight through to `updateOrderStatus`, so `app.current_user_id` got set to the customer's own id; the trigger that records `order_status_history.changed_by` (a staff-only FK to `auth.users`) then rejected the write with `23503` ("A referenced record is missing or still in use.") for every signed-in customer's cancel, guests unaffected. Fixed in `cancelOrderByCustomer` itself (forces `userId: null` on the ctx it hands to `updateOrderStatus`, whatever the caller passed) rather than at the action layer, so no future caller can reintroduce it — the same fix `createOrder`/`createReservation` needed (section 6's identity incident). Guarded by `tests/customer-db-identity.test.ts`.
15. **Coupons need the privileged connection for every customer-facing read, not just `getCouponById`.** `coupons` has no `app_runtime` select policy at all (`coupons_team_select`, migration 0006, is staff-`coupons.view`-only) — a guest or customer applying a promo code is never staff, so the plain RLS-scoped `.query`/`.queryOne` convenience silently returns zero rows regardless of the coupon's real validity. Found 2026-09-28: `getCouponByCode` (every "Apply promo" click) and `countCouponUsageByPhone` (the `usageLimitPerCustomer` check, which also can't work under `orders_customer`'s RLS — that policy only ever exposes the visitor's own `customer_id` rows, never another customer's, so counting "has this phone used it before" restaurant-wide is structurally impossible under `app_runtime`) both used the RLS-scoped read and were fixed to `.write`/`asService`, matching `getCouponById`'s existing comment on exactly this rule. Symptom before the fix: every live, active coupon said "not valid" for any customer, and a per-customer usage cap never actually limited anything. Guarded by `tests/coupons-rls.test.ts` (asserts these two go through `write`, never `query`/`queryOne`). **When a repository function reads a table and it seems to return nothing for no reason, check the table's RLS policy and what `ctx` fields it needs before assuming the query itself is wrong** — this is the same lesson as section 16's `email_verification_codes`/`cart_items` incidents, now a third instance.
16. **A promo code's rules are checked with the throwing validator, never a discarded `tryCalculatePricing` result.** (The database-cart `validatePromoCode` once called `tryCalculatePricing` and ignored `ok`, so a code failing minimum-order/date/order-type/usage checks looked applied until checkout; fixed 2026-09-28.) In the tray: `services/cart.ts#previewCoupon` (cart "Apply") uses `validateCouponOrThrow`; `priceTray` (checkout page) drops a code that no longer applies with a visible `couponNotice`; `createOrder` uses the throwing `calculatePricing`.
17. **A coupon can be restricted to specific customers (added 2026-09-28).** `coupons.eligible_emails`/`eligible_phones` (`text[]`, migration `0025`, default `'{}'` = open to everyone). Admin pastes a newline/comma-separated list of emails and/or phone numbers in the coupon form (`coupon-manager.tsx`); `server/validation/coupons.ts#parseCouponEligibility` splits and normalises it (emails lowercased, phones normalised to E.164 when they parse as one — **must include a country code, e.g. `+92...`**, since that's the only format a real customer's stored phone is ever compared against; an entry that doesn't parse is kept as typed rather than silently dropped). Enforcement is one check in `server/domain/pricing.ts#validateCouponOrThrow` (`CouponPricing.eligibleEmails`/`eligiblePhones`): when either is non-empty, the customer's own email or phone must be in it or the coupon throws the exact same `COUPON_INVALID`/"not valid" as a wrong code — a restricted coupon's existence is never revealed to someone it wasn't given to. `createOrder` always has both (checkout requires a signed-in, verified customer — section 16 — so `input.customer.email`/`.phone` are always real); at the cart-level "Apply promo" (`checkCouponAction` → `previewCoupon(…, customer)`), the signed-in account's email/mobile are read ONLY when the code is restricted (one read; an ordinary code stays database-free) and are unavailable for a guest, so a restricted coupon is rejected for a guest at that step even if they're the intended recipient — they see it validate once they sign in and re-apply. The checkout page's `priceTray` is given the profile's email/mobile (`options.customer`); the layout's re-preview of an already-applied code (`getInitialTray`) skips the restriction (no identity, no DB on page views). `createOrder` is still the one true, unbypassable boundary, same precedent as rule 11's payment-method check.

## 6. Database and environment

- Roles: `app_owner` (migrations/seed, bypasses RLS), `app_runtime` (RLS enforced), `app_service` (BYPASSRLS, server-side writes; the notification dispatcher uses it). On Supabase's pooler a single login is used and `Database` does `set local role` per transaction.
- `DATABASE_URL_SERVICE` is **optional; leave it empty** (the normal setup, including Supabase). Empty = the runtime connection is reused and each write transaction does `set local role app_service`. It only exists for a setup that has a separate login able to act as `app_service`; `app_service` itself is a `nologin` role (created in 0006), so you cannot copy a connection string for it from any dashboard. Setting it wrongly (e.g. to the runtime or owner URL) gains nothing; only set it if you deliberately created a dedicated login role granted `app_service`.
- `.env.example` is a template and must stay free of real values. If it (or any tracked file) ever contains real keys, remove them, keep the values only in `.env.local`, and rotate every exposed secret (DB password, Supabase service-role key, Resend, FCM, `AUTH_SECRET`).
- **Transaction framing is ONE round trip** (`database.ts#beginWithContext`, 2026-09-28): `begin` + role (`set_config('role', …, true)` ≡ `SET LOCAL ROLE`) + request context go as one simple-protocol message, values through `client.escapeLiteral`. It used to be three sequential round trips (`begin`, `set local role`, `set_config`) before every transaction's first statement — ~0.6–0.9 s of pure overhead each on the hosted pooler. ## 7. Notifications (email + push)

Order confirmation and completion **emails** (Resend) and order-status **push notifications** (Firebase Cloud Messaging). Everything is optional: with no provider configured, orders work exactly as before and each channel is skipped (logged), never failed.

| Event | Email | Push |
| --- | --- | --- |
| Order placed (right after the order is committed) | no: the customer only sees "order received" on screen | no |
| confirmed (staff accept the order) | yes: confirmation | no |
| preparing | no | yes |
| ready | no | yes |
| out for delivery | no | yes |
| completed | yes: thank-you + **Rate Your Order** button | yes |
| cancelled | no | yes |

**Reservation emails** (same outbox, table `notification_events` with `reservation_id`; email only; templates `templates/reservation-emails.ts`; `RESERVATION_EMAIL_EVENTS` in `rules.ts`):

| Event | Email |
| --- | --- |
| request submitted (`pending`) | yes: "Reservation request received", status **Pending confirmation**, not a confirmation |
| status becomes `confirmed` (staff, SQL, or auto-confirm at insert) | yes: "Reservation confirmed" |
| cancelled / seated / anything else | no (unchanged) |

Trigger `enqueue_reservation_notification` (0017) queues the event in the booking transaction; `bookTableAction` calls `dispatchDueNotifications` in `after()`, so the mail goes out right after the response and a mail failure can never fail the booking (the success screen is shown once the row is saved). `unique (reservation_id, event_type)` means repeating or bouncing the status (`confirmed → pending → confirmed`) never sends a second email of the same kind; Resend also gets `Idempotency-Key reservation-<id>-<event>-email`. Skipped (not failed) when the guest has no email, no provider is configured, or the restaurant has `notifications`/`emailNotify` off. The booking email field is **required**. The admin status control (`app/admin/(dashboard)/reservations/actions.ts#updateReservationStatusAction`) calls `dispatchDueNotifications` in `after()` (added 2026-09-26; before that a staff confirmation waited for the scheduler). Any other code that changes a reservation status must do the same. `tests/dispatch-wiring.test.ts` fails if an action in `src/app` calls `placeOrder`/`bookTable`/`changeOrderStatus`/`changeReservationStatus` without `after(() => dispatchDueNotifications(...))`. Email **verification codes** never go through the outbox: `sendVerificationCode` (`services/customer-auth.ts`) sends synchronously through `getEmailProvider()` while the customer waits, so there is nothing for the scheduler to pick up. Test by hand: `update reservations set status = 'confirmed' where confirmation_code = '...'` then `npm run notifications:dispatch`; inspect `select event_type, status, email_state, last_error from notification_events where reservation_id is not null`.

The matrix and the push wording live in one file: `server/notifications/rules.ts`; email templates in `server/notifications/templates/`. New status/event = edit `rules.ts` (+ trigger only for a new event source), the table above and `tests/notifications.test.ts`.

### How it works

```
order insert / status change ──(DB trigger, same transaction)──► notification_events   (outbox)
                                                                        │  unique (order_id, event_type)
        checkout action (after response) ─┐                             ▼
        POST/GET /api/internal/notifications/dispatch (cron) ─┬─► NotificationService.dispatchDue()
        npm run notifications:dispatch ───┘                      ├─ EmailProvider → Resend
                                                                 └─ PushProvider  → FCM
```

- The order code never calls Resend or FCM (architecture test). It only commits; the trigger writes the event in the same transaction, so an event exists **iff** the change was committed. A failed order creates no event, so no email.
- Because the trigger is in the database, it does not matter *who* changes a status: the storefront, a future admin screen, or a manual `update orders set status = ...` all queue the same event.
- Events are delivered afterwards, in batches, with per-channel state (`email_state`, `push_state`). A provider outage delays a message (retries after 1, 5, 15, 60 minutes, at most 5 attempts) but never fails or rolls back an order. A retry never resends a channel that already succeeded.
- Events older than `NOTIFICATION_MAX_AGE_HOURS` (default 24) are dropped (`dead`, "expired before delivery") instead of being sent late.
- Repository: `repositories/notifications.ts` (claim with `for update skip locked`, lock 5 min so a crashed worker's rows are re-claimed; load context; save outcome). Tables: `notification_events`, `customer_push_tokens` (server-only, RLS on with no runtime policy, `app_service` granted).

**Duplicate protection (three layers):** (1) `unique (order_id, event_type)`: an event can be queued once (`PREPARING → PREPARING` fires no trigger; a completed order cannot move again). (2) `for update skip locked` claiming plus per-channel state: two dispatchers never take the same event and a retry skips a channel marked `sent`. (3) Resend gets `Idempotency-Key` `order-<id>-<event>-email`. Push has no idempotency key, so each push carries the web notification `tag` `order-<id>-<status>`: if it is ever sent twice (crash between send and saving the result) the device replaces the first one instead of showing two.

### Per-restaurant switches (`restaurants.features`)

Server env vars say whether the **platform** can send; each restaurant additionally opts in via the JSONB column `restaurants.features` (no migration needed):

```json
{ "notifications": true, "notificationChannels": { "emailNotify": true, "pushNotify": true } }
```

| `notifications` | `emailNotify` | `pushNotify` | Result |
| --- | --- | --- | --- |
| true | true | true | email + push (as in the matrix) |
| true | true | false | email only; "Notify me" hidden, push registration refused |
| true | false | true | push only |
| false | any | any | nothing is sent |

- A channel is on only when `notifications` **and** its own flag are true. Missing keys count as **true**, so existing restaurants keep working.
- Checked at delivery time (`NotificationService.deliver`): the trigger still queues the event and a disabled channel is marked `skipped`. Turning a channel on later does not resend events already processed. Changes take effect immediately (no restart/redeploy).
- Schema: `restaurantFeaturesSchema` (`shared/contract/settings.ts`); logic: `notificationChannelsEnabled` (`shared/notification-channels.ts`), the only place that interprets the flags. The order page uses `getPushClientConfigFor(restaurant)`; `registerPushToken` refuses when push is off. An admin screen should write the same keys.

```sql
select slug, features->'notifications' as notifications, features->'notificationChannels' as channels from restaurants;

update restaurants
   set features = features || '{"notifications": true, "notificationChannels": {"emailNotify": true, "pushNotify": false}}'::jsonb
 where slug = 'bella-napoli';                                   -- email only
update restaurants set features = features || '{"notifications": false}'::jsonb where slug = 'bella-napoli';   -- everything off
```

`||` replaces the whole `notificationChannels` object, so always give both flags.

### Behaviour under load

- **Scheduler route drains the queue:** one call keeps claiming batches of 20 until nothing is due or 30 s passed (`drainDueNotifications`, `maxDuration = 60`), so a backlog is not limited to one batch per minute.
- **One dispatcher per restaurant per process, at most 3 overall** (`dispatchDueNotifications`): a call that arrives while one runs flags a re-run and waits for it, so its own event is still picked up and dozens of checkouts do not fight page requests for pool connections (`DB_POOL_MAX`). Across instances, `skip locked` still guarantees one dispatcher per event. `drainDueNotifications` is not coalesced (it must see its own batch size).
- **Email is paced** to `EMAIL_MAX_PER_SECOND` per process (default 2 = Resend's default account limit; raise on a paid plan), so bursts are spread instead of rejected with 429 (2/s = 120/min per process). A 429 that still happens is retried (1, 5, 15, 60 min).
- Verified by `tests/notifications-concurrency.test.ts` (3 restaurants × 40 orders, 48 concurrent dispatchers: every email/push exactly once, right customer, no cross-restaurant leaks, a failed push does not resend the email) and `tests/notifications-dispatch-control.test.ts` (single-flight, cap, drain, email rate, push tag). These use an in-memory store and fake providers, not the real DB/Resend/FCM.

When FCM answers `UNREGISTERED`/invalid, the row is set `is_active = false` with a reason and never used again.

### Links in emails (any device)

Guest orders are normally visible only to the browser that placed them (cart cookie). Emails carry a signed **order-access token** (`?t=…`, 60 days, names exactly one order, cannot be used as a staff/customer session; `signOrderAccessToken`). The order page, review page and push registration accept it as proof. The review button points at `/r/<slug>/reviews?order=<number>&t=<token>` (same table, moderation, one review per order).

### Admin portal: required when it is built

Changing an order's status only **queues** the notification (`status = 'pending'`); nothing is sent until the dispatcher runs. So every admin action that changes a status **must** trigger it, like `placeOrderAction`:

```ts
// src/app/admin/.../actions.ts  ('use server'; app/ may call services, never repositories)
import { after } from "next/server";
import { dispatchDueNotifications } from "@/server/services/notifications";

export async function updateOrderStatusAction(restaurantId: string, orderId: string, status: OrderStatus) {
  return action(async () => {
    await changeOrderStatus(restaurantId, orderId, status, actor);   // service → repositories/orders.updateOrderStatus
    revalidatePath(...);
    after(() => dispatchDueNotifications({ restaurantId }, { restaurantId }));   // never throws, never affects the change
  });
}
```

- **Confirm** must set `confirmed` (that sends the confirmation email). If the UI jumps `pending` → `preparing`, no confirmation email is sent; always go through `confirmed` or change `rules.ts`.
- Call the dispatcher after **every** status change, or pushes stay queued. Keep the scheduler as a safety net (retries, crashed requests).
- Do not send email/push from the admin action itself.

### Other notes

- **Per-restaurant databases:** repositories go through `getDb({ restaurantId })`, events and tokens live with their order, reads are pinned to the event's `restaurant_id`. With one DB per restaurant, the dispatch route/script must run `dispatchDueNotifications({}, { restaurantId })` once per restaurant (or per `DatabaseDirectory` entry).
- **Replacing a provider:** implement `EmailProvider`/`PushProvider` (`server/notifications/types.ts`) in `server/integrations/` and change the two lines in `getNotificationService()`.

## 8. Live order tracking (SSE)

The customer order page (`/r/<slug>/order/<number>`) shows status changes the moment the database row changes. Nothing is polled; no Redis, WebSocket server or extra service, and no key in the browser.

```
update orders set status = …  (staff / SQL editor / future admin UI)
   └─ trigger notify_order_change ─► pg_notify('order_changes', {id, restaurant_id, status, payment_status, estimated_ready_at, updated_at})   (on COMMIT)
        └─ ONE LISTEN connection per server process (server/db/listener.ts, fan-out per order id)
             └─ GET /r/<slug>/order/<number>/events  (SSE; services/order-events.ts openOrderStream; repositories/order-events.ts watchOrderChanges)
                  └─ browser EventSource (components/storefront/use-order-events.ts) → OrderLiveProvider / OrderLiveStatus / LiveOrderTimeline
```

Live page (SSE), push (FCM) and email (Resend) are three separate mechanisms. Pure rules (parse, dedupe, stale events, timeline patch) are in `shared/order-live.ts`.

**How a stream works:** (1) the page renders from the DB as always. (2) The browser opens `EventSource('/r/<slug>/order/<number>/events[?t=<email token>]')`. (3) The route proves access with the same check as the page (`findVisitorOrder`: cart cookie, signed-in customer or signed `?t=`); no proof → 404 and the browser does not retry. (4) The server **subscribes first, then reads the current order and sends it as the first event** (snapshot), so a change between render and subscription, or while offline, is never missed; every reconnect starts with a fresh snapshot. (5) Then each NOTIFY for this order id (and restaurant) is sent as `event: status`. (6) The browser runs each state through `nextLiveState`: stale or identical states are ignored; otherwise badge and timeline update at once and the page re-renders **once** (300 ms debounce) so ETA, history and review link catch up. (7) On `completed`/`cancelled` the server ends the stream and the browser closes it. A `: ping` comment every 25 s keeps proxies from closing an idle connection.

**Security:** the browser never touches the database. A stream follows exactly one order id and events are dropped unless `restaurant_id` matches. The NOTIFY payload has ids, statuses and timestamps only (no personal data). Guest order visibility relies on RLS: verify it is on (section 6).

**Failures:** `DATABASE_URL_LISTEN` unset → route 503, no "Live" marker, page works with its Refresh button. Browser drop → `EventSource` reconnects (`retry: 5000`) and the snapshot re-syncs; "Reconnecting…" after 4 s; after 5 failures in a row without any event the browser stops for that page view. Database connection drop → server reconnects with back-off (1 s … 30 s) and re-reads open orders. Closing the tab/finished order closes the stream; the LISTEN connection closes 30 s after the last stream ends.

**Setup:** apply migration 0015; set `DATABASE_URL_LISTEN=<session-mode or direct Postgres URL>` (LISTEN does not work through a **transaction** pooler; Supabase: pooler host with port **5432**, or `db.<ref>.supabase.co:5432`; it may use the same user as `DATABASE_URL`); restart `npm run dev`; the order page shows a green "Live" marker. The old Supabase Realtime vars (`NEXT_PUBLIC_SUPABASE_ANON_KEY`, `SUPABASE_JWT_SECRET`) are unused; delete them.

**Manual test** (order page open): run the status `update` statements from section 7; badge and timeline move within about a second; in DevTools → Network `events` is one long-lived `eventsource` request. Also try: refresh, two tabs, DevTools Offline then online (catches up), another browser without the cookie (404). `npx vitest run tests/order-events.test.ts tests/architecture.test.ts` runs the DB-free checks.

**Limitations:** needs a long-lived Node process (`next start`, Docker, VM); on serverless short limits the browser reconnects and the snapshot re-syncs, but each instance opens its own LISTEN connection. One shared LISTEN per process; with per-restaurant databases run one per database. When the backend is extracted, expose the same `/events` endpoint (`use-order-events.ts` only needs its URL).

### My Orders (`/r/<slug>/orders`) vs Current Orders (`/r/<slug>/current-orders`) (2026-09-22, split)

Two separate routes sharing one service call (`getMyOrders`, unchanged shape `{signedIn, current, previous}` — no duplicate SQL, no new repository query):

- **`/orders` (My Orders) = history only, signed-in customers only.** Renders `previous`. A guest (no `rp_customer_session`) gets a "Sign in to see your orders" card (Sign In / Sign Up buttons), never any order data — a guest's in-progress order lives at `/current-orders` instead, not here.
- **`/current-orders` (Current Orders) = active orders only, guest or signed-in.** Renders `current` (`ACTIVE_ORDER_STATUSES`) for whoever the request identifies (customer session or guest cart cookie, via `getVisitorContext` — same ownership proof as everywhere else, never the URL). Each card reuses `OrderLiveProvider` + `OrderLiveStatus` (SSE per order; `router.refresh()` re-renders the page when one finishes, which drops it out of `current` — nothing moves it to `/orders` live, the guest just stops seeing it since guests have no history view at all).

Why split instead of one page with two sections (the pre-2026-09-22 shape): "current" needs to work for a guest with zero setup (they just ordered), "previous" fundamentally needs an account (there is nothing to scope history to for a guest beyond the single cart cookie in play right now) — collapsing them into one gated page meant a guest either saw nothing (wrong, they have an active order) or the sign-in prompt hid their own live order. See DECISIONS.md §23.

**Floating current-orders widget** (`current-orders-widget.tsx`, rendered by `app/r/[restaurantSlug]/layout.tsx` on every page, bottom-right): a round badge with the active-order count, linking to `/current-orders`; renders nothing at zero. The count comes from `getMyOrders` in the layout itself — **one extra DB read per page view**, unlike the cart-count cookie hint (rule 10 above), because an order's status changes from *outside* any action this browser takes (staff/SQL update the row), so there is no action to keep a cookie hint current with. Accepted cost given the hosted-pooler latency (~0.3 s) noted in section 6; if this becomes a problem, the fix is a short-TTL hint refreshed by the order page's own SSE stream, not a synchronous read on every route.

`site-header.tsx` also takes a `customer: {signedIn, name}` prop (from `getCustomerSessionSummary`, `account/actions.ts`) and shows Sign In / Sign Up or an Account link next to the existing cart button, desktop and mobile. The phone number and the old "Order online" pill were dropped from the header (2026-09-22); the cart is now an icon-only round button (badge hidden at 0) and Sign In/Sign Up is a filled pill.

**Sign In / Sign Up dialog, tried then reverted (2026-09-22 → 2026-09-23):** for one day the header trigger opened `AuthDialog` (`components/storefront/auth-dialog.tsx`, Radix `Dialog`) as a small centered box over the current page instead of navigating to `/account/sign-in`. **Reverted on 2026-09-23 at the requester's explicit direction** ("Sign In and Sign Up should open on a separate/new page, matching the previous implementation/flow") — `site-header.tsx` now links straight to `/account/sign-in` again (both the desktop pill and the mobile menu item), same as before the dialog existed. `auth-dialog.tsx` is left in the tree unused (not deleted — reverting its one caller was the minimal, requested change; nothing imports it now, so it costs nothing at build time). `SignInForm`/`SignUpForm` still carry the optional `onAuthenticated`/`onSwitchToSignUp`/`onSwitchToSignIn` props from that day (harmless when omitted, which is now always — the standalone pages don't pass them) — if the dialog is ever revived, wiring it back in is a one-file change to `site-header.tsx`, not a forms rewrite. `site-header.tsx`'s `googleEnabled` prop is now unused inside the component (only the dialog read it) but was left on the interface/call site rather than touched, since removing it is unrelated to what was asked. "Continue with Google" itself — the OAuth redirect flow described below — was **not** touched by this revert; it was already a full-page navigation before the dialog existed and still is.

**Reorder** (order detail page, completed/cancelled orders only): `ReorderButton` → `reorderAction` (`order/actions.ts`) → `reorderOrder` (`services/orders.ts`). Ownership of the past order is re-proven with `findVisitorOrder` (not trusted from the click). `buildReorderLines` (repository, previously unused — see the old note this replaces) returns the order's lines at today's ids; each is re-added with the real `addToCart` (service, not a parallel cart mechanism), so pricing is always current, never copied from the old order. An item that is deleted, disabled, or outside its availability window makes `addToCart` throw a `PricingError` (`AppError`); `reorderOrder` catches that per line, skips it, and reports it by name from the order's own item list — one bad line never fails the whole reorder. Lands on `/cart` with a toast naming anything skipped.

## 10. Deploy

### Vercel

1. Push the repo, import it in Vercel (Next.js; build `npm run build`, no output-dir override).
2. Settings → Environment Variables (Production, plus Preview if used): copy every variable from `.env.local` with these differences: `NEXT_PUBLIC_SITE_URL=https://<your-domain>` (used in email links; not localhost); `DATABASE_URL` = Supabase **pooled** string (port 6543; serverless needs the pooler); `DB_POOL_MAX` small (3-5); `FCM_PRIVATE_KEY` on one line with literal `\n`; `NOTIFICATIONS_DISPATCH_SECRET` = a **new** random value; `CRON_SECRET` = the **same value** (Vercel Cron sends `Authorization: Bearer $CRON_SECRET`; the route only checks `NOTIFICATIONS_DISPATCH_SECRET`).
3. Run migrations against the production DB from your machine (`npm run db:migrate` with `DATABASE_URL_MIGRATOR` pointing at it), before deploying code that needs them.
4. Add a cron in `vercel.json` (the file does not exist yet): `{ "crons": [{ "path": "/api/internal/notifications/dispatch", "schedule": "* * * * *" }] }`. Vercel Cron issues **GET** (the route accepts GET and POST). Per-minute schedules need a paid plan (Hobby is limited to daily jobs; check current Vercel limits); on Hobby use an external scheduler.
5. Redeploy after any env change. Verify: `curl.exe -X POST https://<domain>/api/internal/notifications/dispatch -H "Authorization: Bearer <secret>"`, place a test order, check Vercel Logs.

**Live order SSE on Vercel is degraded:** `.../events` needs a long-lived Node process (`runtime = "nodejs"`); serverless functions time out, so the browser reconnects and re-syncs from the snapshot and each instance opens its own LISTEN connection. For real-time use a persistent Node host, or leave `DATABASE_URL_LISTEN` unset and rely on Refresh.

### Other hosting

**Persistent Node host** (Railway, Render, Fly.io, VPS, Docker) is the best fit: `npm ci && npm run build && npm run start` (`next start -p 3000`) behind an HTTPS reverse proxy; same env vars; `DATABASE_URL_LISTEN` can be the direct URL. Behind nginx/Caddy disable response buffering for `/r/*/order/*/events` (the app sends `X-Accel-Buffering: no` and a ping every 25 s).

**Scheduler for the dispatcher** (anything that can make an HTTP call every minute):

| Scheduler | How |
| --- | --- |
| Vercel Cron | above |
| GitHub Actions | `on: schedule: - cron: "*/5 * * * *"` running `curl -fsS -X POST $URL/api/internal/notifications/dispatch -H "Authorization: Bearer $SECRET"` (secrets in repo settings; minimum interval 5 min) |

The scheduler is a safety net (retries, changes made in SQL, crashed requests), not the primary path for checkout. One call drains the whole queue, so a per-minute schedule is enough.

## 13. Future: moving the backend out, one database per restaurant

**Moving the backend out.** `src/server` and `src/shared` import no framework code (the architecture test fails otherwise). To run them as a standalone service: (1) move both into the backend package (keep the `@/server` / `@/shared` aliases); (2) add an HTTP layer (Fastify/Hono/Express or route handlers): each server action becomes a route `schema.parse(body)` → the same service function → `jsonError()`; (3) replace `web/session.ts#getVisitorContext` with middleware that builds the same `RequestContext` from the cookie/Authorization header (`server/auth/tokens.ts` already signs/verifies JWTs; share `AUTH_SECRET`); (4) in the frontend replace `openStorefrontCart`, `getVisitorContext` and the service calls in pages with an API client (components and `shared/` untouched; `revalidatePath` stays in the frontend). Expose the same SSE `/events` endpoint.

**One database per restaurant (not implemented).** `SingleDatabaseDirectory` answers every question with the one configured database. The seam is complete: repositories call `getDb({ restaurantId })`, the registry asks a `DatabaseDirectory` which `DatabaseConfig` holds that restaurant, and `DatabaseManager` keeps one `Database` per config `key`. To enable: (1) store the mapping centrally (JSON file or a `restaurant_databases` table: `restaurantId, slug, key, runtimeUrlRef, serviceUrlRef`; only *references* to env/secret names); (2) implement `DatabaseDirectory` (e.g. `RegistryDirectory`) and construct it in `manager()` in `registry.ts` (`tests/database-registry.test.ts` shows the contract); (3) resolve slug → restaurant first (`getRestaurantBySlug`, `listPublicRestaurants`, sign-in flows call `getDb()` with no restaurant); (4) close gaps: repository functions that look rows up by id only (`getCartById`, `getLocationById`, `updateMenuItem`, …) rely on `ctx.restaurantId` (`grep -rn "getDb(ctx)" src/server/repositories`), make the directory throw on `null` for tenant repositories in dev/test; (5) migrations and seeding run per database; (6) auth needs nothing (sessions carry `restaurantId`); (7) run one notification dispatch and one LISTEN per database.

## 15. Storefront cache (in-memory snapshot, one instance = one restaurant)

Decision record: `DECISIONS.md` §19.

```
instrumentation.ts ─ register() ─► startStorefrontCache() ─► loadStorefrontSnapshot()
                                                               └► repositories/storefront.loadStorefrontData()
storefront GET ─► web/storefront ─► services/{storefront,catalog,restaurants,reviews}
                                       └► snapshotForRestaurant()/snapshotForSlug() ─► memory (0 SQL)
carts, checkout, orders, payments, reservations, customers, write paths ─► services ─► repositories ─► db
```

- At startup `instrumentation.ts` loads a frozen snapshot of the public storefront (restaurant, website, pages, locations, delivery zones, active menu with variants/add-ons, top-50 reviews + summary) for `NEXT_PUBLIC_DEFAULT_RESTAURANT`. Storefront GETs then send **no SQL**. Refresh every `STOREFRONT_CACHE_REFRESH_INTERVAL_MS` (atomic swap, single-flight, chained timer; the old snapshot is kept when a refresh fails or times out). A failed first load fails startup: production exits non-zero, dev keeps the server up and requests error until the cause is fixed. `STOREFRONT_CACHE_ENABLED=false` restores per-request database reads.
- The cache lives on `globalThis` (Next bundles the startup hook and routes separately; dev reloads re-evaluate modules). No SQL in `server/cache` (architecture test).
- New public read-mostly data: add it to `repositories/storefront.ts` → `cache/types.ts` + `storefront-snapshot.ts` → a `read*` function in `storefront-queries.ts` → the service (cache branch + DB branch). Anything transactional or price-deciding stays off the snapshot.
- The snapshot prices the tray PREVIEW (cart page, checkout page: menu via `catalog#getOrderableMenuItems`, zones via `restaurants#getDeliveryZones`, promo codes via `coupons#findPreviewCoupon` — active coupon definitions are in the snapshot since 2026-09-28 and coupon admin writes invalidate it). It never decides what is CHARGED: `createOrder` re-reads restaurant, customer, menu, zones and coupon (with usage limits) inside its own transaction. `server/cache` must still not be imported by cart/checkout/pricing directly (architecture test) — go through the catalog/coupon/restaurant services.
- Snapshot objects are frozen and shared: never mutate what a service returns; copy first.
- After an admin write call `getStorefrontCache().invalidate()`; `server/services/menu-admin.ts` (section 16) does this on every category/item/variant/add-on write.
- With the cache on, other `/r/<slug>` values are 404 (one restaurant per instance).
- The startup hook is the one place outside `server/config` allowed to read `process.env.NEXT_RUNTIME` (Next replaces the literal at compile time so the Edge bundle does not pull in `pg`).

**Still database-bound on purpose:** `/reservation` (one range query, ~3 s on the hosted DB), `/checkout` (one read: the account's profile + addresses + verification, one transaction), placing the order (one transaction), sign-in (one read), the layout's active-orders widget for a signed-in visitor (one read), order tracking. The tray (cart) and the signed-in header state need no database at all.

**Speed facts (hosted Supabase pooler, ~0.3 s per round trip, so one DB transaction of 5 statements is ~1.5 s):** `next start` serves cached storefront pages in ~25–150 ms with 0 SQL; `next dev` compiles each route on its first visit (4–12 s) and renders unoptimised afterwards (0.3–1.8 s), so judge speed on a production build. The snapshot load takes ~7–17 s at start, before the server answers. The cache is per process: on serverless hosts every cold start repeats the load.

**Observing SQL without editing code:** run the server with `NODE_OPTIONS="--require <spy.cjs>"` where the spy patches `pg` `Client.prototype.query` through `Module._load` (match any module exposing `Pool` and `Client`, not only the request string `"pg"`) and logs each statement with its duration. Each Next dev recompile spawns a worker that prints its own "installed" line; exclude it when counting statements.

**If startup fails with `[cache] storefront cache initialization failed`:** the log line carries the database error. `relation "…" does not exist` (code 42P01) means the code and the database schema disagree (for example a migration applied without the matching code, or the reverse): compare `schema_migrations` with `db/migrations/` and check the table names.

## 16. Customer accounts (sign-in, Google, email verification)

**Status (2026-09-22): built and applied, wired into the header/UI.** Sign-in/sign-up/Google/email-verification work end to end from their own pages (`/r/<slug>/account/...`), the checkout gate is live, migration `0018` is applied, and phase 2 (header auth state, cart icon, floating current-orders widget, reorder) is also done — see section 8's "My Orders vs Current Orders" for that half.

**The session identifies the customer; page views never ask the database (2026-09-28).** The customer JWT (`rp_customer_session`, HS256 with `AUTH_SECRET`) carries `customerId`, `restaurantId`, `name` and now `emailVerified`. `auth-service.ts#resolveCustomer` is synchronous and reads only those claims — it used to run `getCustomerById` (a full transaction) and `getStorefrontCustomer` was not request-cached, so a signed-in page view paid ~4 customer lookups (layout summary, visitor context, page). Consequences: a claim can be stale, so (1) `verifyEmailCodeAction` and `updateProfileAction` re-sign the cookie (`web/session.ts#refreshCustomerSession`); (2) anything that ACTS on the account still reads the row (profile, addresses, codes), and placing an order locks and re-checks it inside the order transaction (`createOrder`: row must exist at this restaurant, `is_email_verified` when `requireVerifiedEmail`); (3) a token signed before the claim existed resolves `emailVerified: null` (unknown) — `isSignedInWithVerifiedEmail` then does one read, the checkout page reads it with the profile anyway. A deleted account keeps a working header until the cookie expires or they sign out, but can do nothing with it. **Sign-in** (`signInAction`) = restaurant from the snapshot + ONE read (`id, password_hash, full_name, is_email_verified`) + scrypt; it used to be five transactions. **Sign-up** sends its verification email in `after()` (after the response). `assertCanPlaceOrder` is now sync and only checks the session (SIGN_IN_REQUIRED); EMAIL_NOT_VERIFIED comes from the order transaction. Tests: `tests/customer-session.test.ts` (one transaction per sign-in, claims round-trip, no-DB resolve), `tests/order-access.test.ts`.

**OTP verify + where a customer lands after signing in (2026-09-29).** (1) Checking a code is ONE statement in ONE transaction: `repositories/email-verification.ts#attemptVerificationCode` (CTE: find the active code `for update`, count the attempt, consume it when the hash matches, `update customers set is_email_verified = true`) returning `expired | locked | wrong | verified`; `services/customer-auth.ts#verifyEmailCode` maps those to the same messages as before. It was four transactions (~12 pooler round trips, several seconds) and racy; `recordVerificationAttempt`, `consumeVerificationCode`, `markCustomerEmailVerified`, `isEmailVerified` are gone. Tested for real in a rolled-back transaction on the dev DB (~260 ms) and DB-free in `tests/email-verification.test.ts`. (2) **No `router.refresh()` after a cookie-setting action.** Next 15 answers any server action that sets a cookie with the current route freshly rendered and clears the client router cache (`x-action-revalidated`, `pathWasRevalidated` in `action-handler.js`), so the header already shows the signed-in state. The verify flow used to render three times (VerifyEmailForm refresh, then push + refresh) before the next screen appeared. Sign-in, sign-up, verify, and Google-phone now do one `router.replace(dest)` (replace, so Back doesn't reopen the sign-in form) and prefetch `dest` on mount. `VerifyEmailForm` keeps its button disabled ("Verified") while the caller navigates. (3) **`signInAction` sends the code itself** (`after()` → `ensureVerificationCode`) when the account is unverified. The form no longer calls `ensureVerificationCodeAction` (which was a second request plus an account read). (4) **Landing = `shared/return-to.ts#afterAuthPath(slug, returnTo)`**: the page they came from, else the storefront home `/r/<slug>`, **never `/account`** (that screen is gone since master's 2026-09-28 change: `/account` redirects home, the profile drawer holds profile/addresses/sign-out, and the dock shows "Orders" when signed in). The header pill and mobile-dock sign-in links carry `?returnTo=<current path>` (`signInHref(slug, pathname)`; the dock takes `signedIn`). Checkout already sends `returnTo=/r/<slug>/checkout`, so a customer who had to sign in from checkout (including the verify step) goes straight back to place the order. The Google callback and `GooglePhoneForm` use the same rule. The code hint now says the code expires in 10 minutes, which matches `CODE_TTL_MINUTES`; it used to say 60 seconds, which is really the resend cooldown.

**Forgot password (2026-09-29).** A "Forgot password?" link next to the Password label in `SignInForm` swaps the form for `components/storefront/forgot-password-form.tsx`. Because it lives inside `SignInForm`, it works on `/account/sign-in` and in the checkout/reservation `AuthDialog` alike. It has three steps:
1. **Email:** `requestPasswordResetAction` → `services/customer-auth.ts#requestPasswordReset`. It gives the same answer whether or not an account has that email, so no account enumeration. It is rate limited per caller (`password-reset-request-ip`, 5 per 15 minutes) before the lookup, so unknown emails count too. For an existing account it calls the existing `sendVerificationCode(..., "reset")`, which uses the same code table, 10-minute TTL, per-customer limits and Resend provider. The email template takes `purpose: "verify" | "reset"` for its wording.
2. **Code:** `verifyPasswordResetCodeAction` → `verifyPasswordResetCode` → the existing one-transaction `attemptVerificationCode` (expired, locked after 5 attempts, or wrong; same messages; resend has a 60-second client cooldown). An unknown email gets the same "That code is not correct." as a wrong code. Success returns a 15-minute **reset token** (`auth/tokens.ts#signPasswordResetToken`, purpose `password-reset`). It carries no `sub`/`customerId`, so it can never pass as a session.
3. **New password + confirm:** `resetPasswordAction` → `completePasswordReset` → `auth-service.ts#resetCustomerPassword`. That is one transaction: lock the row, check that the token's `ph` (sha256 fingerprint of the current `password_hash`) still matches, write the new scrypt hash, and set `is_email_verified = true`, because the code proved inbox ownership. It then sets the session cookie and the form calls the sign-in form's `finish()`, which lands on `returnTo` or home. The fingerprint makes the token **single-use** without a new table: after any password change it no longer matches.

There is no migration. `email_verification_codes` has no `purpose` column, so reset and verify codes share it. A code only proves inbox ownership either way, so they are interchangeable. Add a column only if the two ever need different lifetimes or limits. Google-only accounts (no `password_hash`) can use this to add a password. Known limit: existing sessions on other devices are not signed out (JWT sessions cannot be revoked without a denylist). Tests: `tests/password-reset.test.ts` (DB-free: enumeration-safe request, rate limit, code outcomes, token is not a session, single use, cross-restaurant token refused, schema rules, email wording). The same change fixed the verification email's HTML saying "expires in 60 seconds" (the text part and the real TTL are 10 minutes).
**Manual end-to-end** (needs a real inbox): `/r/<slug>/account/sign-in` → Forgot password? → your account's email → code from the email → new password twice → you land signed in. Sign out and sign in with the new password; the old one must fail. Re-submitting the same reset step fails with "already been used".

**Customer login lives on `customers` itself — there is no separate customer identity table (as of `0021_customers_own_login.sql`, 2026-09-23).** `customers` gained `password_hash`, `is_email_verified boolean`, `google_sub`, `auth_provider default 'password'`, `last_sign_in_at`. A customer's login was always effectively restaurant-scoped (a `customers` row already only exists at the restaurant they ordered from), so putting the login fields on the row itself instead of a shared identity table needs no cross-restaurant lookup step. Two partial-unique indexes enforce one account per email/Google-sub per restaurant among non-guest rows: `customers_restaurant_email_key` (`restaurant_id, lower(email)) where not is_guest and email is not null`) and `customers_restaurant_google_sub_key` (`unique (restaurant_id, google_sub)` — NULLs don't collide, so guests/no-Google rows are unaffected). `repositories/customers.ts` has the auth-facing functions: `getCustomerByGoogleSubOrEmail` (privileged bootstrap, matches by either), `linkGoogleToCustomer`, `createGoogleCustomer`, `markCustomerEmailVerified` — plus the ordinary `getCustomerById`/`upsertCustomer`. `email_verification_codes.customer_id` (renamed from `user_id`) FKs straight to `customers(id)` now. There is no `User` type or `Customer.userId` field any more — `Customer` (`shared/contract/models.ts`) carries `emailVerified`/`authProvider` directly.

**Why this changed twice in two days, and why auth.users is staff-only again:** `auth.users` (Supabase's shim, 0001) can never be granted real INSERT/UPDATE for `app_service`/`app_runtime` — confirmed independently on **two different branches** sharing this hosted dev DB (`GRANT ...` on it runs without error but silently grants nothing; only `supabase_auth_admin` can actually write it). The first fix (2026-09-22 → 23, `0019_replace_users_table.sql`/`0020_merge_user_auth_into_users.sql`, now superseded) replaced `auth.users` entirely with an app-owned `users` table shared by staff and customers alike. That collided with a second, independent fix on a parallel admin-portal branch (`0017_grant_app_service_auth_users.sql`/`0018_app_service_auth_schema_usage.sql`/`0019_app_runtime_auth_schema_usage.sql` — different files, note the numbering collision since both branches picked "0017-0019" independently) which kept staff on `auth.users` and tried granting `service_role` membership instead — also confirmed not to actually enable INSERT/UPDATE (same "no privileges were granted" wall), but that branch's admin/staff code (`auth-service.ts`, `team.ts`, `scripts/db/create-staff.ts`) was built assuming `auth.users`, and running both branches' migrations against the one shared DB left it in a mixed state (the `users`-table FKs got silently reverted to `auth.users` and `users` emptied by whichever branch's script ran last — there is no real "merge" between two schema designs solving the same problem differently). **Resolution, at the requester's explicit direction:** stop needing a shared identity table for customers at all (this section) — `auth.users` goes back to being staff/admin-only, exactly as the other branch already has it, untouched by anything here; `scripts/db/create-staff.ts` (that branch) still creates staff via the migrator connection, never a live request. The two systems don't share a table any more, so they can't collide on one again. See DECISIONS.md §26 for the full incident writeup.

**Migration `0018_customer_auth.sql`:** the surviving piece is `email_verification_codes` (RLS on, no `app_runtime` policy, `app_service` only — same pattern as `notification_events`); verifying a code sets `customers.is_email_verified`.

**Config:** `googleAuth` section (`GOOGLE_CLIENT_ID`, `GOOGLE_CLIENT_SECRET`) — same optional-until-configured pattern as `push`/`email`; `config.googleAuth` is `null` and "Continue with Google" is hidden on every page until both are set. No Google SDK dependency: `server/integrations/google.ts` does the OAuth2 authorization-code flow by hand and verifies the returned `id_token` with `jose` (already a dependency) against Google's published JWKS.

**Email verification (checkout gate):** `server/services/customer-auth.ts` (`sendVerificationCode`, `ensureVerificationCode` — only sends when no still-active code exists, `verifyEmailCode`, `isEmailVerified`). A 6-digit code, HMAC-SHA256-hashed with `AUTH_SECRET` (not scrypt — codes are short-lived, rate-limited, and don't need scrypt's cost), 10-minute expiry, 5 max attempts, sent through `getEmailProvider()` (new export in `services/notifications.ts` — the same Resend provider the outbox uses, but called synchronously since a customer is waiting on screen, not through `notification_events`). **Guests are never gated** — verification only applies to a signed-in customer's login email (`visitor.userId` set, which since `0021` is the customer's own id); there is no email-verification requirement for guest checkout, matching the existing guest architecture (a guest `customers` row has `is_email_verified = false` and no password/google_sub, but nothing ever checks it). The gate itself lives in `checkout/actions.ts#placeOrderAction` (throws `errors.custom("EMAIL_NOT_VERIFIED", ...)`, a new `ErrorCode`) and is enforced server-side — `checkout-form.tsx` only uses the `EMAIL_NOT_VERIFIED` code to swap in `<VerifyEmailForm>` instead of a generic error toast; hiding the form field client-side would not have been enough.

**Ordering requires a signed-in, verified customer (2026-09-26, at the requester's direction; supersedes "Guests are never gated" above and the `allowGuestCheckout` setting, which is now ignored but still parses).** Rule: `services/customer-auth.ts#assertCanPlaceOrder(visitor)`, called first in `checkout/actions.ts#placeOrderAction`: no customer session → `SIGN_IN_REQUIRED` (new `ErrorCode`, HTTP 401), signed in but unverified → `EMAIL_NOT_VERIFIED`. That server check is the real gate; the UI only follows it: `/checkout` redirects a guest to `/account/sign-in?returnTo=/r/<slug>/checkout`; the cart's action reads "Sign in to check out" (same link) with a one-line reason; the checkout form turns `EMAIL_NOT_VERIFIED` into the inline verify-code step and `SIGN_IN_REQUIRED` (session ended mid-checkout) into a redirect to sign-in. Guests can still browse, fill a tray (the tray is kept through sign-in: the cart cookie is unchanged), book tables and track orders they placed earlier. **returnTo:** sign-in / sign-up pages read `?returnTo=`, sanitised by `shared/return-to.ts#safeReturnTo` (only `/r/<this-slug>/...`, never absolute/protocol-relative/cross-tenant or the auth pages themselves; the one sanitiser, also used by the Google flow and google-phone); forms push there after sign-in / after verifying a new account, Google carries it, and the sign-in ↔ sign-up links keep it (`signInHref`). Tests: `tests/order-access.test.ts` (rule + open-redirect cases); e2e: guest is redirected; the full order flow needs `E2E_CUSTOMER_EMAIL`/`E2E_CUSTOMER_PASSWORD` of a verified account (skipped otherwise).

**Google sign-in and the mandatory-phone problem:** `customers.phone` is `not null` and part of `unique (restaurant_id, phone)`, but Google never provides a phone number. `completeGoogleAuth` therefore does **not** create a `customers` row itself: if one already exists for `(restaurant, google-linked user)` it signs in directly; otherwise it mints a short-lived (`signGooglePendingToken`/`verifyGooglePendingToken` in `auth/tokens.ts`, purpose `google-pending`, 15 min) token and the browser is sent to `/account/google-phone?token=...` to collect a phone before `finishGoogleSignup` creates the `customers` row and the real session. Do not "fix" this by inventing a placeholder phone — it would collide with the next Google-only customer at the same restaurant under the unique constraint.

**Flow:** `GET /r/<slug>/account/google` (redirects to Google, stores CSRF `state` in a short cookie `rp_google_state` via `web/session.ts#setGoogleState`) → Google → `GET /r/<slug>/account/google/callback` (`code`+`state`, verified against the cookie via `consumeGoogleState`) → either signed in or redirected to `/account/google-phone`.

**"Continue with Google" returns to wherever it was clicked, not a hardcoded `/account` (added 2026-09-23, still true after the dialog revert above):** the OAuth round trip has to leave the page (redirect to accounts.google.com and back) regardless of whether sign-in itself is a dialog or a standalone page — this piece isn't about the dialog, it's about the redirect target. **Session cookie:** `rp_customer_session` (`CUSTOMER_COOKIE`) was defined since the original build but never set anywhere — `getStorefrontCustomer`/`getVisitorContext` could only ever read it. `web/session.ts#setCustomerSession`/`clearCustomerSession` (new) are what `account/actions.ts` calls after `signInCustomer`/`createCustomerAccount`/Google/`finishGoogleSignup` succeed. **The same "RLS context missing `customerId`" bug hit two more places (fixed 2026-09-23, found right after the `resolveCustomer` fix below made real signed-in sessions reach these code paths for the first time):**
- **`cart_items`/`carts` writes** (`new row violates row-level security policy for table "cart_items"` when a signed-in customer added to cart): `cart.ts#cartContext(restaurantId, cartToken)` never included `customerId`, but `cart_is_owned`'s RLS check (0005) is `(customer_id is not null and customer_id = app.current_customer_id()) or (customer_id is null and session_token = app.cart_token())` — once a cart has `customer_id` set (any signed-in customer's cart, set by `openCart`), the token-based branch no longer applies and the customer-id branch needs `ctx.customerId`, which was never passed. Every `cartContext(...)` call site in `cart.ts` (`addToCart`, `updateCartItem`, `removeFromCart`, `emptyCart`, `applyCoupon`, `changeOrderType`, `changeCartLocation`) now takes the cart's `customerId` and passes it through; `findCart`/`readCart` (`web/storefront.ts`) and `checkout.ts#placeOrder` now also pass the signed-in visitor's `customerId` so the *read* doesn't get RLS-blocked either (a signed-in customer's cart could no longer even be found, not just written to). Guest carts (`customer_id is null`) are unaffected — this only bit carts already linked to a customer.
- **`email_verification_codes` reads** (a verification code always says "expired" even entered seconds after being sent): `getActiveVerificationCode` (`repositories/email-verification.ts`) was the one function in that file still on the default `app_runtime` read; that table is RLS-enabled with **no** `app_runtime` policy at all (server-only, same as `notification_events` — 0018), so it always returned zero rows regardless of timing. Fixed by switching it to `write`/`asService` like the other three functions in the file already were.

Both are the same lesson as the `users`/`resolveCustomer` fixes above: a table with no `app_runtime` RLS policy, or a policy keyed on something `ctx` doesn't carry, needs every read *and* write routed through `write`/`asService` — the default `getDb(ctx).queryOne`/`.query` convenience is `app_runtime`-scoped and silently returns nothing instead of erroring, which is what made all of these look like "sometimes it just doesn't work" rather than a clear failure. **When a repository function reads or writes a table and the result seems wrong/empty/blocked for no reason, check the table's RLS policy and what `ctx` fields it needs before assuming the query itself is wrong.**

**Sign-in now also gates on email verification, not just checkout (added 2026-09-23):** `signInAction` already returned `emailVerified` in its result but `SignInForm` ignored it. It now checks `result.data.emailVerified` after a successful sign-in: if false, the action itself sends a code (`ensureVerificationCode` in `after()`, same "only send if none active" helper checkout uses; since 2026-09-29, before that the form called `ensureVerificationCodeAction`) and renders the same `<VerifyEmailForm>` inline instead of finishing sign-in; verifying calls the same `finish()` (toast + close dialog/navigate) that a normal sign-in does. Works in both the modal (`AuthDialog`) and the standalone `/account/sign-in` page since `VerifyEmailForm` doesn't care which one it's in. Google sign-in is not gated this way — Google emails are marked verified at creation (`createGoogleCustomer`/`linkGoogleToCustomer` always set `is_email_verified = true`, since Google already verified it) so there is nothing to gate. (`upsertGoogleUser` named here originally no longer exists — see the `0021` note above; the behavior is unchanged, just on `customers` now.)

**`resolveCustomer` silently signed every customer back out (fixed 2026-09-23):** `customers`' only SELECT policy is `customers_self: id = app.current_customer_id()` (0006), and `app.current_customer_id` is only set from `ctx.customerId` (`database.ts#applyContext`). `resolveCustomer` (called by `getStorefrontCustomer` on every `/account`, `/orders`, checkout page load) looked the customer up by `user_id` via `getCustomerByUserId` — passing `userId`/`restaurantId` in ctx but never `customerId` — so under `app_runtime` (RLS-enforced) `app.current_customer_id()` was always null and the policy blocked every row, no matter how valid the session cookie was. Google sign-in (or any sign-in) would succeed, set the cookie, redirect to `/account` — which then immediately bounced back to `/account/sign-in` because it could never find the customer. Fixed by having `resolveCustomer` use `getCustomerById(session.customerId, { customerId: session.customerId, restaurantId })` instead — `session.customerId` is already in the JWT, so there's no need to rediscover it by `user_id`, and passing it as `ctx.customerId` satisfies the RLS policy the way every other owner-scoped query already does (section 6's RLS note). **This bug predated all the `users`-table churn above and affected every customer sign-in method, not just Google** — grep any future "signed in but immediately signed back out" report for `app.current_customer_id` first. (`getCustomerByUserId`, named here originally, no longer exists post-`0021`; its bootstrap-lookup role is now `getCustomerByGoogleSubOrEmail`, same privileged `write`/`asService` shape.)

**Phone numbers:** `server/validation/common.ts` gained `e164Phone` (validates + normalises to E.164 via `libphonenumber-js`, new lightweight dependency) alongside the older, looser `contactPhone` (kept for reservations, which this phase did not touch). **Phone country picker: Radix `Select`, not a native `<select>` (changed 2026-09-23).** Requirement: once a country is picked, the closed field shows only "🇵🇰 +92" (flag + calling code), while the open dropdown still lists "🇵🇰 +92 Pakistan" (flag + code + name) for every country. A native `<select>` can't do this — its closed box always renders the matched `<option>`'s own text, so closed and open can't differ. **Verification code resend has a 60-second cooldown (added 2026-09-23).** `VerifyEmailForm` (shared by sign-up, the sign-in gate, and the checkout gate) now starts a `secondsLeft` countdown at 60 on mount (a code was just sent by the caller right before this form renders) via one `setInterval` for the component's lifetime, clamped at 0 — not recreated every tick, so there's no double-counting or drift from repeated effect setup. "Resend code" is disabled and reads "Resend code in Ns" while `secondsLeft > 0`; clicking it while disabled is also a no-op in `resend()` itself (defense in depth, not just relying on the disabled attribute). A successful resend resets `secondsLeft` back to 60; the same interval keeps counting it down. This is a client-side UX cooldown only — the server-side rate limit on `sendVerificationCode` (3/5min per user, 8/15min per IP, `server/services/customer-auth.ts`) is the real guard against abuse and was already there.

## 18. Online payments (Stripe card, JazzCash wallet)

`server/integrations/payments.ts` is the `PaymentProvider` abstraction (`isConfigured`, `supports(method)`, `createIntent`). `getPaymentProvider(method, onlineProvider)` — **`onlineProvider` (the restaurant's `settings.payments.onlineProvider`, one of `"none"|"stripe"|"jazzcash"`) picks the gateway for `card_online`/`wallet`**; without it, the first provider in the list whose `supports()` matched would win regardless of what the restaurant configured (harmless while only Stripe existed, wrong the moment a second online provider — JazzCash — also claims `wallet`). Cash/terminal methods always use the cash provider regardless of `onlineProvider`.

- **Stripe** (`card_online`) is real, via Stripe Checkout (hosted page) — plain REST + `fetch`, no `stripe` SDK dependency, same "no SDK, no extra dependency" convention as `integrations/resend.ts`. `server/integrations/stripe.ts`: `createCheckoutSession` (bracketed form-encoding for nested params — `toFormBody`), `retrieveCheckoutSession` (re-fetches the session from Stripe's API with our own secret key — the actual trust boundary for the return route, since a `session_id` in a URL alone proves nothing), `verifyWebhookSignature` (Stripe's documented `t=...,v1=...` HMAC-SHA256-over-`"ts.rawBody"` scheme, timing-safe compare, 300s replay tolerance). **Test-mode keys are free and instant** at Stripe's dashboard (Developers → API keys) — unlike JazzCash, no business/merchant onboarding needed to get `sk_test_...`/`pk_test_...` keys; that's why Stripe was the first gateway actually wired end-to-end (2026-09-26) despite JazzCash being requested first — JazzCash's sandbox was unreachable/slow to obtain credentials for at the time. PKR is a supported Stripe presentment currency, so no currency conversion is needed even though Stripe doesn't operate/pay out in Pakistan (irrelevant in test mode; revisit before any live key).
- **Env:** `STRIPE_SECRET_KEY` + `NEXT_PUBLIC_STRIPE_PUBLISHABLE_KEY` (both required, though the publishable key isn't actually used by the Checkout-redirect flow — kept for a future embedded-Elements option), `STRIPE_WEBHOOK_SECRET` (optional but recommended — see Return vs webhook below). Admin settings → Payments → "Online payment provider" = **Stripe**, `card_online` enabled.
- **Stripe flow:** `createIntent` returns `{redirectUrl}` (a plain GET, unlike JazzCash's POST form) to Stripe's hosted Checkout page; `checkout-form.tsx` does `window.location.href = redirectUrl` (`PlaceOrderResult.payment.kind === "redirect"`, vs `"form"` for JazzCash — the two gateways need different client-side navigation, hence the discriminated union). `restaurantId`/`orderId`/`orderNumber` travel in the Checkout Session's `metadata` (and again in `payment_intent_data.metadata`, so a `payment_intent.*` event would carry them too) — the webhook has no restaurant slug in its URL (it's one global endpoint, not per-tenant), so it resolves the restaurant from metadata alone, not from a request path.
- **Return vs webhook — both call `confirmOnlinePayment`, safely (it's idempotent):** the customer-facing return route (`checkout/pay/stripe/route.ts`, `GET`, Stripe's `success_url`) re-fetches the session and redirects the browser to the order page immediately; a customer who closes the tab mid-payment never reaches it. The webhook (`api/internal/payments/stripe/webhook/route.ts`, `POST`, configure in the Stripe Dashboard or `stripe listen --forward-to localhost:3000/api/internal/payments/stripe/webhook` locally, events `checkout.session.completed` + `checkout.session.async_payment_failed`) is Stripe's recommended source of truth and fires regardless. Skipping the webhook (leaving `STRIPE_WEBHOOK_SECRET` unset) still lets checkout work; it just means a dropped redirect leaves an order looking unpaid until staff notice.
- **JazzCash** (`wallet`) is real, end-to-end, but **untested against JazzCash's actual sandbox — built 2026-09-26 with no sandbox credentials in hand.** `server/integrations/jazzcash.ts` implements their publicly documented Hosted Checkout Page (HCP) Mobile Wallet flow (`pp_TxnType = MWALLET`): builds the `pp_*` request fields + HMAC-SHA256 `pp_SecureHash` (salted with the Integrity Salt, over every non-empty `pp_`/`ppmpf_` value sorted by key — `computeSecureHash`, exported only for `tests/jazzcash.test.ts`), and verifies a return the same way (`verifyReturn`). **Verify the exact field list/order against the Integration Guide PDF JazzCash sends with sandbox credentials** — a hash mismatch shows up as `pp_ResponseCode "999"` on the return; adjust the field list there if so.
- **Env:** `JAZZCASH_MERCHANT_ID`, `JAZZCASH_PASSWORD`, `JAZZCASH_INTEGRITY_SALT` (all three, or JazzCash stays unconfigured), `JAZZCASH_ENV` (`sandbox`|`live`, default sandbox). Get them from JazzCash's sandbox merchant self-onboarding. A restaurant also needs admin settings → Payments → "Online payment provider" = **JazzCash**, and `wallet` in its enabled methods, before "Wallet" appears at checkout — `getCheckoutOptions` (`server/services/checkout.ts`) gates `wallet` exactly like `card_online` (`features.onlinePayments` AND `onlineProvider !== "none"` AND the provider actually configured); it used to skip that gate entirely for `wallet`; showing "Wallet" with nothing behind it.
- **Flow (both gateways):** `placeOrder` (`server/services/checkout.ts`) calls `getPaymentProvider(...).createIntent`, whose result becomes `PlaceOrderResult.payment` — a discriminated union: `{kind: "redirect", redirectUrl}` (Stripe, plain GET) or `{kind: "form", formAction, formFields}` (JazzCash, needs a real browser POST). `checkout-form.tsx` branches on `kind`: `window.location.href = redirectUrl`, or `submitWalletForm()` builds a hidden `<form>` client-side and submits it. `returnUrl` is built from `provider.id` (`/r/<slug>/checkout/pay/<provider.id>`), not the payment method, since one method (`wallet`) could map to different providers later. The order is already committed at this point (same as a cash order) — a failed `createIntent` call does **not** undo it, only marks the payment `failed` and shows a "contact the restaurant or choose cash" error; this mirrors an unpaid COD order, not a rollback.
- **Return:** JazzCash POSTs to `pp_ReturnURL` = `/r/<slug>/checkout/pay/jazzcash` (`route.ts`, `POST` only); it verifies the hash (never acts on an unverified payload) and looks the order up via `ppmpf_1` (orderId) + `pp_BillReference` (orderNumber) through `getOrderForAccessGrant` (same privileged, service-role lookup pattern as the email order-access-token — the verified hash IS the proof). Stripe redirects (`GET`) to `/r/<slug>/checkout/pay/stripe`, which re-fetches the session from Stripe instead (see above) — different verification mechanism, same shape. Both call **`confirmOnlinePayment`** (`server/services/checkout.ts`, renamed from `confirmWalletPayment` once Stripe needed it too), which is idempotent (a resolved payment is left alone, so a retried/duplicated callback is harmless) and **only ever changes `payment_status`** (`orders.payment_status` + the `payments` row, via `setOrderPaymentStatus` — fixed 2026-09-26 to write both; it used to touch only `payments`, so nothing else in the app — order lists, the SSE trigger, admin filters — ever reflected a call to it, and it was dead code until JazzCash's callback started using it). `orders.status` (the staff-driven kitchen state machine, section 5 rule 4) is untouched: a paid online order still needs a staff `confirm`, same as cash. Both return routes end by redirecting the browser (303) to the order tracking page, which already shows the true `payment_status` on the next `trackOrder` read (no query-param banner needed) and gets it live via the existing SSE trigger (`orders.payment_status is distinct from new.payment_status`, migration `0015`) since the redirect target is a fresh page load anyway.
- **No DB migration needed for either gateway:** `payment_method.wallet`/`card_online` and `payments.provider` (free `text`) already existed; only `settings.payments.onlineProvider`'s zod enum gained `"jazzcash"` (JSONB, no schema change).
- **Testing:** `tests/jazzcash.test.ts` (hash build/verify round-trip, tamper rejection, non-`000` codes) and `tests/stripe.test.ts` (webhook signature verify/tamper/wrong-secret/replay) are both DB-free and cover the correctness-critical, pure-function part of each gateway. Neither can exercise a real sandbox/test-mode call end-to-end here: JazzCash still has **no sandbox credentials in hand** (built 2026-09-26 against their publicly documented scheme — verify the exact field list/order against the Integration Guide PDF they send with credentials; a hash mismatch shows up as `pp_ResponseCode "999"`); Stripe's return/webhook routes need a public HTTPS URL (ngrok over `localhost`, or `stripe listen` for the webhook specifically) since both gateways redirect/POST to a real internet address, never `localhost`. Once credentials exist for either: set its env vars, set a restaurant's `onlineProvider` accordingly and enable the matching method, place an order, and watch `select payment_status, provider, status, failure_reason from orders join payments on payments.order_id = orders.id where order_number = '...'` after the redirect back.

## 20. The tray (cart) is a cookie; placing the order is the one database transaction

Decision record: `DECISIONS.md` §28 (and §29 for the session/transaction-framing side). Rebuilt 2026-09-28: there is no database cart at all any more (the `carts`/`cart_items` tables still exist, unused; `repositories/carts.ts` is gone).

```
QuickAddButton / ItemCustomizer / cart page ─► useLocalCart() ─► document.cookie "rp_tray_<slug>"      (no request)
layout (every page)   ─► web/storefront#getInitialTray ─► decodeTray(cookie) ─► services/cart#viewTray  (snapshot, no DB)
/cart "Apply" promo   ─► checkCouponAction ─► previewCoupon ─► coupons#findPreviewCoupon                (snapshot, no DB)
/checkout             ─► readTrayView + getDeliveryZones (snapshot) + priceTray (snapshot)  + getCustomerProfile (1 DB read)
"Place order"         ─► placeOrderAction ─► placeOrder ─► repositories/orders#createOrder   ═ ONE transaction, 5 round trips:
                          1 begin+role+context · 2 ONE read (restaurant, customer FOR UPDATE, whole tray's menu, [zones], [coupon+usage])
                          3 insert order · 4 ONE write (all lines, all add-ons, payment, [delivery], [coupon usage] as CTEs) · 5 commit
                       ─► clearTray(slug)
```

- **Cookie format** (`shared/tray.ts`): `v1!<orderType>!<locationHex|_>!<couponB64|_>!<line>*<line>…`, line = `<itemHex>.<variantHex|_>.<qty>.<addonHex~qty,…|_>.<noteB64|_>`. Cookie-safe characters only (no percent-encoding), UUIDs as 32 hex, ~40 chars per plain line; `TRAY_COOKIE_MAX_CHARS` 3800 (browsers cap a cookie at 4 KB) — `addLine` returns `false` and the UI toasts "Your tray is full" rather than silently losing a line; max 50 lines. Not HttpOnly (the browser writes it); `decodeTray` is tolerant — anything malformed is dropped line by line, never thrown — and nothing in it is trusted for money.
- **Display vs. contents:** the cookie holds ids and quantities only. How a line looks (`TrayLineDisplay`: name, image, variant, add-on names, unit price, add-ons total, `problem`) comes from the server on a page load (`getInitialTray` → `viewTray`, current menu prices) or from the add button's own menu data for a line just added. `LocalCartProvider` starts from the server's `initial` (so SSR and the first client render match — no empty-then-filled flash, no `hydrated` flag any more), writes the cookie on every change, adopts a new `initial` when the server re-renders the layout with a different cookie, and calls `router.refresh()` on focus/visibility when another tab changed the cookie.
- **One resolver:** `server/domain/menu-selection.ts#resolveMenuSelection` (pure) decides availability, variant/add-on rules, defaults and prices for BOTH the preview (snapshot `MenuItem`s via `catalog#getOrderableMenuItems`) and the order (rows from `repositories/menu.ts#orderableItemsSql` inside the order transaction). It is a rule-for-rule port of the old `resolveItemSelection`. A preview line that fails resolution is shown with its `problem` and blocks Checkout until removed.
- **Checkout page:** 404-free redirect to `/menu` when the tray is empty; pricing = `priceTray` (same `calculatePricing`); a promo code that no longer applies is dropped with a visible `couponNotice` and the form submits only the code actually shown as applied (`placeOrder` uses `input.couponCode`, never the tray's stale one). One DB read: `getCustomerProfile` (customer row + addresses + `emailVerified`, one transaction, `repositories/customers.ts#getCustomerWithAddresses`).
- **`createOrder`** (`repositories/orders.ts`): the statement budget is fixed — 5 round trips for any order (1 line or 50, pickup or delivery with a coupon), +1 only when a signed-in customer's account has no mobile yet (`saveFirstAccountPhone`, one `update … where not exists (clash)` statement). Order-item ids are generated in Node (`randomUUID`) so add-ons can reference their line inside the same batched statement. Data-modifying CTEs are safe here: FKs between them are checked at statement end, `payment_to_order` only recomputes `payment_status` (still `pending`), `sync_delivery_from_order` only reacts to a status change. `orders.cart_id` is written `null`. The read projects only needed columns (`ORDER_RESTAURANT_COLUMNS`, `ORDER_CUSTOMER_COLUMNS`, `orderableItemsSql`) — see section 6 on response size.
- **Measured (hosted pooler, 2026-09-28, every commit rewritten to rollback):** place order = 1 transaction / 5 round trips for 1, 3 or 5 lines and for delivery + coupon; server time for all of it < 5 ms (`explain analyze`: order insert with its 7 triggers 2.9 ms); wall 1.7–2.4 s on a steady link, up to ~3.5–4 s under pooler jitter. The same order before this work: sync the tray (1 transaction, 21 statements for 3 lines, ~8 s) + place order (~6 transactions incl. 3 nested, ~60 statements). Sign-in: 1 transaction / 3 round trips, ~0.9–1.2 s (was 5 transactions). Checkout page profile read: 1 transaction / 4 round trips, ~1.1–1.6 s. Add to cart / change quantity / apply promo: 0 DB.
- **Reorder** (`order/actions.ts#reorderAction` → `services/orders.ts#reorderLines`): reads the past order (its own DB reads — proof of ownership + lines), resolves them against the current menu, and returns lines + displays; `ReorderButton` adds them with `addLines` (reports how many fit).
- **Legacy cookies** `rp_cart` / `rp_cart_n` (database-cart era) are only deleted on sign-out now. Sign-out keeps the tray (it is the browser's, not the account's).
- **Gaps:** a tray is per browser (not synced across a customer's devices — that would need the database again); the e2e spec (`e2e/customer-flow.spec.ts`) still describes the older cart UI copy and was not re-run here (no running app + test account); the DB-backed `tests/checkout.test.ts` was ported to line arrays but needs the local test Postgres to run.
- **Testing:** `tests/tray.test.ts` (codec: round trip incl. unicode notes, cookie-safe charset, tolerance of tampered input, size limit), `tests/local-cart.test.ts` (reducers, `toTray`/`fromInitialTray`), `tests/menu-selection.test.ts` (resolver rules), `tests/create-order-sql.test.ts` (real `createOrder` against a recording fake: one transaction — a nested one throws —, 3 statements inside it for any order shape, account/verification/phone rules, menu prices), `tests/customer-profile.test.ts` (`placeOrder` → one `createOrder` call), `tests/storefront-services.test.ts` (preview on snapshot, order on DB).

## 21. Delivery location & branch selection (Google Maps)

Checkout's delivery step (2026-09-27) lets a customer use their current GPS location, search an address (Google Places Autocomplete), or drag a pin on a map to set the exact delivery point; the resolved city then filters `restaurant1s` (branches) down to that city, ranks them by straight-line distance and recommends the nearest one. No schema change was needed — the columns already existed (`restaurant1s.city/latitude/longitude`, `customer_addresses.latitude/longitude`, `orders.delivery_address` jsonb) — this was wiring, not new tables.

- **Env:** `NEXT_PUBLIC_GOOGLE_MAPS_API_KEY` (optional). Google Cloud Console → enable **Maps JavaScript API, Places API, Geocoding API** on the key; restrict it to HTTP referrers for the site's domain(s) (+ `localhost` while developing) — Maps browser keys are meant to be public, referrer-restricted, not secret. Config: `config.maps` (`server/config/index.ts`) → `{ apiKey } | null`; a server component reads it and hands it to the client as a prop (same pattern as `config.push.web` for Firebase) — client code never reads `process.env` directly, keeping the "process.env only in server/config" rule.
- **No key configured → no regression:** `LocationPicker` (`components/storefront/location-picker.tsx`) renders nothing when `apiKey` is null; checkout and the address book fall back to exactly the plain text fields that existed before this feature.
- **`shared/geo.ts`:** pure, isomorphic `haversineKm`/`sortByDistance` — the only new geometry code; no npm mapping/geo package was added.
- **`components/storefront/location-picker.tsx`:** loads `https://maps.googleapis.com/maps/api/js?libraries=places` once per page (a module-level promise, so mounting it twice — checkout **and** the profile drawer's address form — never double-injects the script). "Use current location" (`navigator.geolocation`), a Places `Autocomplete` search box, and a draggable `Marker`; any of the three reverse-geocodes (`Geocoder`) to `{addressLine1, area, city, postalCode, latitude, longitude}` and calls `onResolve`. Handles permission-denied, no-geolocation-support, and geocode-failure inline (never blocks the manual fields below it). `@types/google.maps` is a dev-only devDependency (types only; the JS itself loads via the script tag, not npm) — install it again if `node_modules` is ever reset from a lockfile that predates it.
- **Branch ranking (`checkout-form.tsx`):** `customerPoint` = the chosen saved address's lat/lng, or the picker's last resolve; `customerCity` same precedence. Branches are filtered to `restaurant1s.city` (case-insensitive) matching `customerCity`, then `sortByDistance` when a point is known. The nearest is auto-selected (`useEffect` keyed on the ranked id list) but a customer can tap any other card in the same city to override it; zero matches shows "We don't have a branch in `<city>` yet." instead of silently keeping the old branch. Only shown at all when the restaurant has more than one active location — a single-branch restaurant never sees this step.
- **How the branch pick actually takes effect:** selecting a card calls the tray's `useLocalCart().setLocationId` (no server action — there is no database cart, section 20) then `router.refresh()`; the checkout page re-reads the tray cookie and re-prices with that branch's zones, and `placeOrder` passes `tray.locationId` to `createOrder`. `local-cart.tsx#commit` writes the cookie synchronously for exactly this: written only from its effect, the refresh could go out with the old cookie and the provider's "adopt the server's reading" effect would undo the pick (found merging master's DB-cart version, which called `setLocationAction`, 2026-09-29). Delivery-zone matching (`matchDeliveryZone`, area/postal-code strings — unchanged, still no geo-radius logic) keys off that same `locationId`.

- **Bug, two fix attempts, real root cause found 2026-09-27: `LocationPicker` crashed the whole checkout page with `NotFoundError: Failed to execute 'removeChild' on 'Node'`, cascading into `Uncaught Error: Rendered more hooks than during the previous render`.** The hooks error is a **symptom, not a separate bug** — every component on the page was audited line by line and none conditionally calls a hook; React's own fiber bookkeeping gets corrupted when a DOM mutation throws mid-commit, and the *next* render after that throws the hooks-mismatch as an unrelated-looking secondary crash. So the real fix is only ever about the `removeChild` error. First attempt (still worth keeping, but insufficient alone): `LocationPicker` mounts/unmounts every time checkout toggles between a saved address and "new address" without tearing down its Google Maps objects on unmount, so an in-flight geocode/dragend/`place_changed` callback could land after unmount and touch removed DOM nodes — fixed with a `mountedRef` guard on every async Maps callback and a real cleanup (`google.maps.event.clearInstanceListeners`, `marker.setMap(null)`, nulling every ref). **That fix did not stop the crash because it wasn't the actual cause.** The real cause: `<div ref={mapDivRef}>{status === "loading-script" ? <Loader2/> : null}</div>` — `new google.maps.Map(mapDivRef.current, ...)` takes ownership of that div's contents and mutates them directly and imperatively, while React *also* believed it owned that div's one child (the loading spinner) and tried to update/remove it independently. The instant Maps touches that node, React's picture of its children is stale; the next time React's own reconciler tries to remove what it thinks is still there, the node is already gone/moved, and `removeChild` throws mid-commit — which is what corrupts the fiber tree and produces the "more hooks" error on the following render. **Fixed by a strict DOM-ownership rule, not a workaround**: both `mapDivRef` and the new `autocompleteContainerRef` (see below) are *bare* containers that never receive React-rendered children — any loading/status UI is an absolutely-positioned **sibling** overlay in a wrapping `relative` div, never a child of the Maps-owned node. This is the general fix for this entire bug class: **never render React children inside a container a third-party imperative library (Maps, D3, a jQuery plugin, ...) also mutates** — reuse this sibling-overlay pattern, don't put a loading spinner or placeholder *inside* the library's own container again.

Requires no new npm package or API version — `PlaceAutocompleteElement` ships in the same `libraries=places` bundle as the legacy widget; `@types/google.maps` ≥ 3.66 has its types.
- **Same change: fixed "Google Maps JavaScript API has been loaded directly without loading=async."** `loadGoogleMaps()`'s script URL gained `&loading=async` (Google's own recommended query param, alongside the `<script>` tag's existing `async` attribute) — the module-level `mapsLoader` promise singleton (one script tag for the whole page, reused by checkout and the profile drawer's address book) was already correct and is unchanged.
- **"Could not resolve an address for that point" on every pin, search or current-location action means the key's project is broken, not the point.** The console logs `[LocationPicker] reverse geocode failed: <status>`. `REQUEST_DENIED` means billing is off on the Cloud project, the Geocoding API is not enabled, or a key restriction blocks it. The key needs billing plus the Maps JavaScript API, Geocoding API and Places API (New) enabled.
- **`PlaceAutocompleteElement` renders as a black box on a light page when the OS is in dark mode**, because it themes itself from the OS. `LocationPicker` sets the element's `color-scheme` from its container's computed value, and sets `background: transparent; border: none` so the container's styling shows.
- **Follow-up fix: `TypeError: e.maps.Map is not a constructor`.** With `loading=async`, the script's `onload` does not mean the API is ready. At that point `google.maps` can lack `Map`/`Geocoder`/`Marker` or even `importLibrary` itself, which caused a follow-up `TypeError: e is not a function`. Readiness is signalled only by the `&callback=__locationPickerMapsReady` URL param. After that, the classes come from `google.maps.importLibrary(...)`, called on `google.maps` (not destructured). `loadGoogleMaps()` waits for that callback, then awaits `importLibrary("maps" | "geocoding" | "marker")` (plus `"places"`, where a failure only warns because search is optional) before resolving. A failed load also resets the singleton so the next mount can retry. Any new Maps consumer must go through `loadGoogleMaps()` and must not check `window.google?.maps` directly.
- **Bug found 2026-09-28: the whole picker (map, current-location, drag-pin) would flash the loading spinner then silently disappear (`status` → `"unavailable"`) whenever *anything* inside the init `.then()` threw — most likely `PlaceAutocompleteElement`'s constructor, e.g. before "Places API (New)" finishes propagating on a freshly-restricted key (Cloud Console: up to 5 minutes) — and the outer `.catch(() => setStatus("unavailable"))` swallowed the real error with no console output, so there was nothing to debug from.** Fixed: the `PlaceAutocompleteElement` setup is now in its own inner `try/catch` (a search-widget failure no longer takes down the map/current-location/drag-pin, which don't depend on it), and both that catch and the outer one now `console.error`/`console.warn` the actual thrown error. **If the picker still disappears, open the browser console — it now names the real cause** (a `RefererNotAllowedMapError`/`ApiNotActivatedMapError` from Maps itself, or a `[LocationPicker]` log from this component) instead of failing silently.

- **Reservations require sign-in only to submit, not to browse (2026-09-27; corrected same day — see below).** Unlike checkout (gated at the page level), `reservation/page.tsx` renders for guests too — a guest can pick a date/time/guests and fill in name/phone/email freely. Reservations do **not** require a *verified* email to submit — only sign-in. The form uses the same `PhoneInput` (E.164, country-code picker) and locked-field pattern as `checkout-form.tsx`: a saved phone or a verified account email is shown read-only ("· from your account") for a signed-in customer; a guest (or an unverified account) gets plain, editable fields, same as before this change. `bookTableSchema.guestPhone` changed from `contactPhone` to `e164Phone` to match. `services/reservations.ts#bookTable` resolves a signed-in visitor's account by id (`attachAccountCustomer`, above) and — mirroring `checkout.ts#placeOrder`'s `savedPhone`/`email` precedence exactly — always uses the account's own saved phone/email over whatever the client sent when one is on file, so a locked field can never be spoofed by editing the request payload. **First attempt at this feature wrongly gated the whole page** (`redirect()` in `page.tsx` before any guest could see the form) — reverted same day once the actual requirement (gate the button, not the page) was clarified; if this needs revisiting, gate the submit, not the route.

### Order sound notifications (admin)

New-order and cancelled-order chimes, audible on any admin page (not only `/orders`), gated behind `orders.view`. No SSE/LISTEN infra exists for a multi-order staff feed (section 8's stream is scoped to one order) — this polls a small JSON endpoint instead, the same tradeoff `KitchenAutoRefresh` already made for the kitchen board, just without a full page refresh.

- **`repositories/orders.ts#listOrderActivitySince(restaurantId, sinceIso, ctx)`** (service: `getOrderActivitySince`): rows where `updated_at > sinceIso`, each flagged `isNew` (`updated_at = created_at` — true only for a row nothing has ever updated since its insert, because every table gets a `set_updated_at` BEFORE UPDATE trigger (migration 0001/0006) that bumps `updated_at` on the first real change; `created_at`/`updated_at` share one transaction timestamp at insert, so they're identical to the tick for a brand-new row). This is how "new order" is told apart from "existing order whose status just changed" without a second column.
- **`orders/activity/route.ts`** (GET, `orders.view`): `?since=<ISO>` → `{ now, events }`. The client advances its cursor to the **server's** `now`, never its own clock, so clock skew can't replay or skip events.
- **`components/admin/order-sound-notifications.tsx`**: `OrderActivityWatcher` (mounted once in `(dashboard)/layout.tsx`, polls every 7s with `fetch` — never `router.refresh()`, so it never re-renders whatever the staff member is actually looking at) plays a short two-note Web Audio chime for a new order and a single lower tone for a cancellation — synthesised with `OscillatorNode`/`GainNode`, no bundled audio asset, no new dependency. `SoundToggleButton` (bell icon, `AdminHeader`, next to Sign out) is a **per-browser** preference (`localStorage rp_admin_sound_enabled`, default on) — deliberately not a `restaurants.settings` key, because this is "does this device make noise," not a tenant-wide business setting. A `CustomEvent` (`rp-admin-sound-pref`) keeps every mounted instance in the same tab in sync (the native `storage` event only fires cross-tab).
- **Autoplay:** browsers refuse to start an `AudioContext` before a user gesture on the page; this is accepted, not worked around (per the brief: "do not attempt to bypass browser security restrictions"). The toggle button's own click is a gesture and resumes/creates the shared `AudioContext` immediately (and plays an audible confirmation chime), so sound works as soon as a staff member has clicked anything once per tab — no separate "enable audio" prompt was needed.
- **No duplicate/repeat sounds:** each poll only returns rows touched since the last cursor, and the cursor always advances, so one status change is seen exactly once across polls; an order that changes status twice between two polls still only produces whichever single event is current at poll time (acceptable — this is a notification, not an audit trail; the admin orders list/detail page is the audit trail).
- **Tone is a short repeating pattern (~1.5s), not one blip** (changed 2026-10-03, at the requester's direction — a single quick beep was too easy to miss on a busy counter): `playChime` plays the same two-note (new order) / single-note (cancelled) pulse three times with gaps, still two clean sine tones rather than a harsh buzzer, and still bounded (not a looping alarm) per the "don't make it annoying" rule.
